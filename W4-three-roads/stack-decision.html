Choose Your Stack, With AI

Four real constraints given up front, three genuine options weighed against them, the front-runner pressure-tested, and a decision made in my own words — not the first answer accepted.

The four constraints given

Budget
Free only — no paid hosting, no paid tools
Honest skill level
Backend-focused (Python/FastAPI/Django). Comfortable with git, HTML/CSS. No prior React/Next.js project experience.
What the portfolio needs to do
Show a sitemap-defined site (Hero → Work → About → Buy), case studies with screenshots, and links out to real repos/demos. Nothing on the site itself needs to be dynamic yet — no accounts, no live database-backed content.
How work must be shown
Image galleries (case-study screenshots), long-form case-study text, and links to external code repos / demo GIFs — not an embedded live app.

Three roads, simplest to most powerful

Road 1 — Static HTML/CSS + GitHub Pages CHOSEN
Build
Hand-written / AI-assisted static HTML, CSS, no build step, no framework
Host
GitHub Pages — free, already connected to my existing repo
Backend
None
Trade-off
Fastest to ship, zero maintenance surface, but every content update means editing HTML directly — no CMS, no templating reuse across pages
Road 2 — Static site generator (Astro / Jekyll) + free hostmiddle
Build
Templated pages, reusable layout/header/footer, still compiles to plain static files
Host
GitHub Pages or Netlify, still free
Backend
None required; a form service (Netlify Forms free tier) could be bolted on later
Trade-off
Solves the "editing HTML by hand" problem as case studies grow, but adds a new tool to learn on top of an already full backend-engineering course load
Road 3 — Next.js on Vercel, with API routesmost powerful
Build
React/Next.js, component-based, optional serverless API routes
Host
Vercel free tier
Backend
Available if needed — could wire into the Supabase project already set up for the Week 4 auth assignment
Trade-off
Most impressive ceiling and the most "real app" feel, but a full JS toolchain, build pipeline, and framework to learn — the biggest mismatch against current skill level and timeline

Pressure-testing the front-runner (Road 1)

What breaks if I pick the simplest?
No built-in image gallery component (hand-coded grid instead), no contact-form backend (would need a third-party free form service like Formspree if ever needed), and reusing a consistent header/footer means copy-pasting across pages rather than a shared layout.
What do I maintain if I pick the most powerful?
A React/Next.js toolchain, dependency updates, a build step that can break, and debugging surface area I don't have experience with yet — on top of an already dense weekly assignment schedule.
Can I finish in two weeks?
Road 1: yes — already built and live (see Week 4's "Empty but Live" deployment). Road 3: risky — no prior Next.js project completed, and the course load leaves little slack for a new framework's learning curve.
Does it show my work the way it needs to?
Yes. Case-study screenshots work as a plain image grid; long-form case-study text is just HTML; the DocuMind agent demo doesn't need to live inside the portfolio — it links out to its own repo, README, and a recorded GIF. The portfolio's job is to point at proof, not host the proof itself.

Decision, in my own words

I'm going with Road 1 — static HTML/CSS on GitHub Pages. I considered a static-site generator (Road 2) and Next.js on Vercel (Road 3), but rejected both for the same underlying reason: neither content-editing convenience nor a live backend actually solves a problem I have right now. My portfolio's content — a sitemap, four case studies, an about section, and a contact action — is fixed and small enough that hand-editing HTML isn't a real burden, and nothing on the site needs to be dynamic; the one thing that is dynamic (the DocuMind agent) already has its own home and just needs a link.

Can I maintain this? Yes — it's the same three files I already understand, on a host I've already configured, with zero moving parts to break between now and the next deadline. If the portfolio outgrows hand-edited HTML later (many more case studies, a blog, recurring content updates), Road 2 is the natural upgrade — not Road 3, since a live backend still isn't something this project needs.

Backend question, answered honestly: not yet. The portfolio itself has no reason to talk to a database or run server logic — that complexity belongs to the projects it links to, not to the site that lists them.
