2 · Embed flow

Step by step

#WhoWhat happens
1OwnerPOST /widgets (authenticated) creates a tenant-isolated widget row
2BackendReturns an embed snippet: <script src="cdn/widget.js" data-widget-id="{id}">
3OwnerPastes the snippet into their site's HTML — a different origin than our API
4widget.jsGET /widgets/:id/config — public, cached, CORS-enabled
5widget.jsRenders the popover/form client-side using the returned config
6VisitorSubmits the form — CORS POST /submissions fires from the customer's origin
7BackendValidate → rate-limit → spam-check → enrich (geo fallback chain) → store → safe side-effect
8OwnerViews submissions + stats on an authenticated, tenant-isolated dashboard

3 · Submission contract

POST /submissions — public, CORS-enabled
Request body:
{
  "widget_id": "uuid",
  "fields": { "email": "visitor@example.com", "name": "..." },
  "honeypot": ""  // must arrive empty — bots tend to fill every field
}
StatusMeaning
201Created — { "status": "received", "id": "uuid" }
400Malformed payload, missing required field, or oversized body
404widget_id doesn't exist or widget isn't active
429Rate limit exceeded — tracked per IP and per widget
GET /widgets/:id/config — public, cached
Response headers:
Cache-Control: public, max-age=300
ETag: "<hash of config + embed_version>"

Response body:
{ "type", "copy", "fields", "targeting", "style", "embed_version" }

CORS policy (both endpoints)

Access-Control-Allow-Origin reflects the requesting origin only if it matches a domain registered on that widget's targeting rules (or is left open for widgets with no domain restriction). OPTIONS preflight is handled explicitly on both routes — this is the most-attacked surface in the whole program, so CORS is enforced server-side, not just assumed from browser behavior.
